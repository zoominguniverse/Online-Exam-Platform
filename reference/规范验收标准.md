# 规范验收标准

## 产品设计

| 条目               | 要写清什么，为什么这样规定                                   | 怎么检查                                                     |
| :----------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| 用户与场景         | 每个页面或能力服务哪类角色、由什么操作触发，写进 README 的「用户与场景」一节。它是需求的下游：每条能力的场景都要落得到某个页面上，落不到的能力说明边界不清 | 反向对照——找出无法落到页面的场景即为遗漏；交叉评审（peer review）逐页核对服务对象 |
| 页面清单与信息架构 | 页面（路由）清单与层级关系；同一功能的入口唯一；非法路径的处理方式（重定向还是 404）。信息架构不稳定会让后续每次新增能力都要重排导航 | 按清单逐个访问；出现清单外的入口或孤立页面即为缺陷           |
| 视图状态完备性     | 每个数据视图必须枚举全部状态——加载中、正常、错误、空状态（empty state），并给出各自的文案模板。状态不完备时，故障表现为界面无响应，而不是明确提示 | 清空数据后逐页观察；断开依赖后观察错误态；出现无限加载或无提示的空白即为缺陷 |
| 文案与术语         | 同一概念全产品用词统一，维护术语表（受控词汇）；错误文案包含三要素——发生了什么、可能的原因、可执行的下一步。术语不一致会连带污染接口字段与文档 | 检索术语表之外的写法；抽查错误提示是否给出下一步动作         |
| 表单与校验         | 校验时机（失焦 / 提交）、提示的位置与粒度、必填标识、提交过程中对重复触发的处理。交互层只负责抑制重复点击，真正的去重由后端的幂等保证 | 逐表单走查；连续点击提交只产生一次结果                       |
| 视觉基线           | 间距刻度、字号层级、语义色（成功 / 警告 / 错误）的用法、基础组件清单。写令牌与层级而不是逐个页面的像素值——后者每次改版都要重排 | 新增页面应复用组件清单中的元素；出现自造样式即判违规         |
| 可达性与响应式     | 键盘可达、表单控件与标签关联、对比度下限、断点矩阵与各断点的布局变化。这是可用性下限，不是附加项 | 键盘走查一遍主路径；按断点矩阵逐个核验                       |
| 变更可追溯         | 产品形态变化时同步更新页面清单与 README，并记入变更说明。缺失追溯关系时，下一次改动无从判断「为什么变成这样」 | 变更说明与 README 对照；出现未同步的差异即为缺陷             |
| 状态与流程         | 有流程的功能必须给出三样东西——状态枚举、状态流转、每个状态下允许的操作；状态只能按规则流转并由后端校验，前端不得直接传目标状态；已终结的状态默认不可修改，确需修改要有明确入口并留痕；同一条记录被多人同时处理时，后操作的人要收到「已被处理」的提示。为什么：目标状态由前端传递，等于把流程规则交给调用方；静默覆盖会让前一次操作的结果无从追溯 | 对已终结的记录发起变更，应被拒绝；两个会话同时处理同一条记录，后一次应收到明确提示，且前一次的结果未被覆盖 |
| 导入导出           | 每个导入功能声明文件大小与行数上限，超限时整体拒绝；导入先校验并预览，由用户确认后执行，整批成功才生效，失败时给出错误明细（行号加原因）并提供模板下载；导出受权限与数据范围限制，敏感字段按脱敏规则导出并留痕，大批量走异步。为什么：部分入库会留下无法解释的半批数据，清理它的成本高于整批重来 | 混入一行非法数据，检查是否整批拒绝且错误明细给出行号；导出结果中的敏感字段应为脱敏值 |

## 后端开发

| 条目               | 要写清什么，为什么这样规定                                   | 怎么检查                                                     |
| :----------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| 分层与依赖方向     | 接口层 → 业务层 → 数据访问层，外部能力收在最外侧的适配层（adapter）；禁止反向依赖与跨层直连。反向依赖一旦出现，改动任何一层都要通读全部代码 | 新增模块落在规定的层即为通过；业务层出现数据访问语句即判违规 |
| 接口命名与版本控制 | 资源用小写复数、路径带版本前缀；HTTP 方法与语义一致（读 GET，写 POST / PUT / PATCH，删 DELETE）；不以动词作路径。版本前缀让新旧契约可以并存一段时间 | 路由清单逐个核对；命名不一致由静态检查发现                   |
| 请求与响应结构     | 成功与失败返回同一套外层结构，含业务码、可读信息、数据、请求标识（request ID），全项目只用这一套。调用方据此写一遍解析逻辑，不必按接口分支 | 接口文档与实现比对；新增接口复用同一响应封装                 |
| 错误码体系         | 错误码分区（参数 / 认证 / 授权 / 业务 / 依赖不可达），各区对应各自的 HTTP 状态；新增错误码登记进清单。即兴编号会让错误处理退化成字符串比较 | 错误码清单与实际返回值比对；出现清单外的错误码即判缺陷       |
| 参数校验的位置     | 校验在接口层边界完成，业务层只接收已校验的数据；校验失败返回统一错误结构。这是快速失败的具体落法：越早拒绝，代价越低 | 故意把必填校验写进业务层，检查是否被指出                     |
| 数据访问与事务     | 查询只出现在数据访问层；事务边界在业务层；结构变更必须条件更新且可回滚。事务跨越多层时，回滚语义就无从说清 | 迁移脚本审查；执行一次回滚验证可逆                           |
| 事务内的禁止项     | 事务内只包含必要的数据库读写与一致性校验；不得夹带外部 HTTP 调用、消息投递、文件上传或长耗时计算；涉及外部通知与异步任务时改用 Outbox 或事件表等最终一致性方案，并写明谁写入、谁投递、失败如何重试与补偿。为什么：外部调用不可回滚——事务回滚之后副作用仍留在对端，且长事务会放大锁冲突 | 在事务内注入一次外部调用，检查是否有检查手段能发现；人为回滚一次，核对外部副作用是否残留 |
| 幂等与并发         | 每个写接口声明是否幂等；同一请求重复送达不产生重复副作用，唯一约束落在存储层而不是应用层判断——应用层判断存在「检查」与「写入」之间的时间窗 | 同一写请求连续发送两次，比对结果；并发场景下重复键应被约束拦截 |
| 分页、排序与筛选   | 参数名与默认上限统一；排序与筛选字段走白名单。白名单之外一律拒绝，避免把用户输入直接拼进查询条件 | 传入白名单外的字段应被拒绝；超过默认上限应被截断             |
| 排序的唯一兜底键   | 排序键不唯一时，必须追加一个唯一键（通常取主键）作为兜底排序条件。为什么：排序不稳定时，同一条记录可能同时出现在两页，也可能一页都不出现 | 构造一批排序键相同的记录，翻两页比对记录集合是否重复或缺失   |
| 非法筛选的失败策略 | 筛选条件不合法（字段不存在、取值越界、类型不符）时返回明确错误，不得按「未传条件」处理，更不得返回全量数据。为什么：这是默认拒绝在查询语义上的延伸——退化为全量，等于把一次越权读放大成全表读 | 传入不存在的筛选字段与越界取值，检查是否明确报错；结果条数不应多于合法查询 |
| 配置外置           | 地址、密钥、特性开关只从环境变量读取；代码中不出现字面量，缺失即启动失败。带默认值继续运行会把配置错误推迟到最坏的时刻暴露 | 删除一个环境变量，应用应启动失败而非带默认值运行             |

## 安全开发

| 条目                     | 要写清什么，为什么这样规定                                   | 怎么检查                                                     |
| :----------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| 默认拒绝（default deny） | 未显式授权即拒绝；新增接口默认不可访问，须显式登记进授权清单。默认允许的系统里，遗漏一处判定就多一个入口 | 新建一个未登记的接口，访问应失败                             |
| 逐资源授权判定           | 授权判定在服务端逐条资源执行，先取行再校验归属（fetch-then-check）；跨资源访问按不存在处理。这是完全中介的具体落法：每一次访问都要判定，不复用上一次的结论 | 换成他人的资源标识重放请求，应被拒绝                         |
| 附件与文件读取           | 禁止提供通用的、仅凭文件标识即可读取或下载的接口；读取必须挂钩业务对象并完成授权判定；附件不落在公开静态目录。为什么：文件标识可以被枚举，通用读取接口等于放弃授权判定——这是越权最常见的漏点 | 换一个账号用原文件标识直接读取，应被拒绝；匿名访问附件地址应无法打开 |
| 越权失败场景             | 每条读写资源的场景必须配对一条越权场景：水平越权（访问同类型的他人资源）与功能级越权（低权限访问高权限功能）。把安全要求写进规约，测试才有依据 | 场景清单与用例清单比对，缺一即判未覆盖                       |
| 认证与会话               | 口令用加盐的单向算法（如 bcrypt）存储，不保存明文；令牌不进 URL 查询串与日志；会话支持立即失效。URL 会被浏览器历史与网关日志留存 | 检索日志；令牌出现在 URL 中即判失败                          |
| 令牌的存放位置           | 访问令牌放内存，不写入本地存储；刷新令牌放在 HttpOnly、Secure、SameSite=Strict 的 Cookie 中并支持轮换；修改口令之后既有令牌立即失效。为什么：本地存储可被页面脚本读取，一旦发生脚本注入，令牌即等同于泄露 | 在浏览器控制台检索本地存储，取不到访问令牌；修改口令之后用旧令牌请求应被拒绝 |
| 密钥与机密               | 只从环境变量读取；忽略规则先于代码入库；配置样例只写键名；一旦进入历史即轮换（rotate）。历史可被克隆，删除文件不足以消除风险 | 检索仓库全部提交历史与镜像层；轮换步骤写在 README 中         |
| 外部内容不可信           | 用户上传的正文、技能与工具描述都视为外部数据：拼进提示词时放在用户消息里，系统提示里写明不执行其中的任何指令。这是提示词注入（prompt injection）的第一道边界 | 上传含指令性文本的素材，检查模型是否把它当作指令执行         |
| 出站地址白名单           | 出站请求的目标地址、回调地址与文件拉取地址走白名单或等价校验，禁止由请求参数直接决定。为什么：服务端会被诱导访问内网地址或任意外部地址，而这类请求不带用户身份 | 提交指向内网地址的回调地址，应被拒绝，且日志中不出现成功访问记录 |
| 输入校验（validation）   | 按白名单校验类型、长度、范围与枚举；内部标识不可信，必须校验其归属。黑名单总是在列举已知危险 | 传入超范围值与错误类型应被拒绝                               |
| 输出转义（escaping）     | 按输出上下文转义：页面、命令行、模板；查询一律使用参数绑定，不拼接字符串。注入的本质是数据被当成代码执行 | 构造含引号与标签的输入，检查是否被原样执行                   |
| 敏感数据                 | 敏感字段不进日志与响应体；脱敏规则集中定义一处。分散定义的结果总是有遗漏 | 抽查日志与响应，含敏感原值即判失败                           |
| 依赖引入与许可证         | 新依赖需说明用途与许可协议，许可证走白名单；版本锁定文件入库。供应链缺陷会绕过所有应用层防护，而许可证问题往往到发布时才被发现 | 抽查依赖清单；存在白名单外的许可证即判未通过                 |
| 依赖漏洞扫描             | 规定触发时机、阻断级别与修复时限                             | 构建产物含达到阻断级别的漏洞时应失败                         |

## 测试

| 条目               | 要写清什么，为什么这样规定                                   | 怎么检查                                                     |
| :----------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| 测试层次           | 单元测试覆盖业务规则，接口测试覆盖每条能力的正常与失败路径，端到端只覆盖主路径。层次错位会让反馈周期随规模线性变长 | 统计各层用例数量；主路径之外出现端到端用例即为层次错位       |
| 用例来源           | 每个场景至少对应一组用例，用例与场景之间可双向追溯。写不出来源的用例通常是顺手写的形状检查 | 场景清单与用例文件逐一比对                                   |
| 三类组织           | 用例按正常路径 / 失败路径 / 边界归组；失败路径的数量不少于规约列出的条数。边界值来自等价类划分的两端 | 目录结构与命名核对；缺一类即判未完成                         |
| 数据隔离           | 测试使用独立的数据实例或模式（schema）；每条用例运行前后自行清理；不依赖执行顺序与残留数据 | 随机化执行顺序，结果应保持一致                               |
| 外部依赖           | 外部服务与时钟用可注入的测试替身；不访问真实外部服务，不依赖真实时间 | 断开网络后测试仍应全部通过                                   |
| 一键运行           | 命令、所需环境变量、退出码、报告位置写进 README；一次命令执行完全部测试。不能被复现的执行过程无法作为验收依据 | 新成员按 README 执行一次                                     |
| 通过判定           | 失败即以非零退出码阻断；不得保留「已知失败」清单；跳过用例必须写明理由并登记 | 构建结果含失败用例时判定未通过；跳过用例数只减不增           |
| 断言有效性的判据   | 判据只有一句：改坏被测逻辑，这个用例会不会变红。这是变异测试思想的轻量用法——只断言形状（不报错、长度相等）的用例在缺陷面前保持沉默 | 对被测逻辑做一次等价的破坏，检查用例是否失败                 |
| 缺陷判定的信号口径 | 先写明本系统用哪套信号——响应中是否有独立于 HTTP 码的业务码；有业务码时成败只看业务码，不套「失败必须 4xx」这类 HTTP 惯例；无业务码时按接口文档写明的 HTTP 码判，文档没写才用兜底表。为什么：把 HTTP 惯例当判据，会把「HTTP 200 且业务码已拒绝」的正确实现误判为不通过 | 取一条 HTTP 200 但业务已拒绝的响应，核对该用例是否被误判为不通过 |
| 缺陷的四个判定词   | 写清「被当成成功」「被放行」「被误拒」「未处理故障」各自的含义；响应中出现堆栈或「系统错误」这类无信息量的文案即算未处理故障。为什么：没有统一的判定词，「用例通过」就无法说明是否存在缺陷，评审也无从比较 | 随机抽五条不通过的用例，两人各自判定是否构成缺陷，结论应一致 |
| 响应时间阈值       | 正向用例的端到端耗时设两档——超过 50 ms 标记，超过 100 ms 判不通过（阈值按项目自定，此处为示例值）；只考核正向用例，负向用例不计入。为什么：单阈值会把「偏慢」与「不可接受」混为一谈，前者应当被看见而不是被阻断 | 每条正向用例记录耗时；落在两档之间的应被标记而不判不通过     |
| 变更要求           | 每次变更至少补写与其场景对应的用例；修复缺陷先补一条能复现该缺陷的用例 | 变更说明与新增用例对照                                       |

## 部署运维

| 条目                             | 要写清什么，为什么这样规定                                   | 怎么检查                                               |
| :------------------------------- | :----------------------------------------------------------- | :----------------------------------------------------- |
| 可复现构建                       | 依赖锁定文件入库；容器化构建（Dockerfile）分阶段，只把运行所需的产物放进最终镜像；镜像用版本号或提交号打标签。不可复现的构建无法定位线上跑的究竟是哪份代码 | 同一提交号构建两次，产物应一致                         |
| 环境与配置                       | 开发 / 测试 / 生产三级环境；同一镜像跨环境，只换配置；密钥与环境变体分开存放。各环境各构建一次时，测试结果不代表生产行为 | 换环境部署无需重新构建镜像                             |
| 健康检查（health check）         | 存活与就绪两个端点分开；就绪未通过不接受流量；收到停止信号先处理完在途请求再退出。两者合一会让「启动中」被当成「已死」而反复重启 | 依赖未就绪时端点返回失败；发起停止后在途请求不被切断   |
| 结构化日志（structured logging） | 单行 JSON；必带请求标识（request ID）、时间戳、级别、模块名；字段命名统一；敏感字段不落日志。可被查询的日志才谈得上观测 | 抽样一次请求，检查各模块日志能否串起同一个标识         |
| 指标与告警                       | 至少定义请求量、错误率、时延、依赖连通四项指标；每条告警写明阈值、责任人与处置动作。没有处置动作的告警等价于噪声 | 制造一次失败，检查告警是否触发并指向责任人             |
| 发布与回滚                       | 采用滚动或蓝绿发布；一键回滚到上一个版本标签；回滚步骤写进 README 并演练过。回滚能力是发布策略的前提，不是补救措施 | 执行一次回滚并记录耗时                                 |
| 数据变更顺序                     | 结构变更先于代码发布且向后兼容：加字段 → 双写 → 切读 → 删旧字段；删除类操作最后执行。顺序颠倒会造成新旧版本之间必然有一段不可用窗口 | 旧版本代码在新结构上应仍可运行                         |
| 备份与恢复                       | 写明备份频率与保留期、恢复目标（RPO / RTO）；定期执行恢复演练。未演练过的备份不能作为恢复依据 | 执行一次恢复演练并记录用时                             |
| 性能与容量                       | 写清时延预算（如列表接口 p95 不超过 500 毫秒）、慢操作阈值、批量大小上限、外部调用配额。没有预算时，「慢」的判断只能靠感觉 | 定期抽样一次时延分布；超预算的接口应能定位到具体调用点 |
| 限流与配额                       | 写接口与成本较高的接口（模型调用、检索）按主体限流；超限时返回明确错误与重试建议 | 连续发起超额请求，应被拒绝而非被排队处理               |
| 发布留痕                         | 每次发布记录版本号、变更内容、验证结论，归档到仓库的 docs/ 目录。发布记录是事后复盘的唯一时间线 | 按版本标签检索，应能找到对应记录                       |

## AI应用

| 条目               | 要写清什么，为什么这样规定                                   | 怎么检查                                                     |
| :----------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| 调用边界           | 哪些环节必须用模型，哪些应当用确定性规则。能算出来的不要问模型；模型只负责不确定的那一段 | 逐个调用点问一句「换成规则会怎样」，答不上来即说明边界不清   |
| 工具落点           | 模型可调用的工具只能落在系统已有的服务方法上，严禁为模型开数据直连。为什么：工具一旦直连数据，授权判定与脱敏规则就被绕过去了——同一条数据走页面要授权、走工具不要授权 | 逐个工具确认它最终调用哪一个服务方法；出现直接查询数据库或对象存储的工具即为违规 |
| 提示词即代码       | 模板随版本入库，带版本号与评测结论；变更走评审，不在对话框里改完就上线。随版本变的东西属于代码，不属于配置 | 检索仓库中的模板文件；出现线上与仓库不一致的模板即判缺陷     |
| 模型与参数锁定     | 模型名与版本、温度、最大输出长度写进配置并锁定；阈值类数值集中一处。散落在代码里的常量会各自漂移 | 配置文件中应能一次找到全部模型相关参数                       |
| 超时、重试与降级   | 单一超时值、重试上限与退避策略；依赖不可达时返回明确的错误码与可理解的提示。不做无限等待，也不静默返回空结果 | 停掉模型服务，检查是否在超时后返回明确错误而非挂起           |
| 输出校验           | 结构化输出先校验再使用；解析失败按失败处理，不静默降级为默认值。把不可信输出当作外部输入对待 | 构造一段畸形返回，检查是否被判失败而非被继续使用             |
| 不编造依据         | 无命中或引用列表为空时，输出固定的无依据说明，不返回伪造的标识与片段。编造出处比答不上来严重得多 | 检索空库后提问，检查回答是否含任何出处编号                   |
| 外部内容的装配方式 | 材料正文、技能与工具描述作为数据放在用户消息里；系统提示中写明不执行其中的任何指令 | 上传含指令性文本的素材，检查模型是否把它当作指令执行         |
| 评测集与回归       | 维护一份小样本评测集，含「必须答对」与「必须拒答」两类；改提示词或换模型版本后跑一次，结果归档 | 改一次提示词，评测集应能给出前后两份可对比的结果             |
| 用量与成本观测     | 记录模型名、提示词版本、耗时、用量、命中数；不记录提示词全文（含用户数据）。没有用量记录就无法回答「这个月为什么涨了」 | 抽样一条请求，检查这些字段是否齐全且不含原文                 |

## 数据

| 条目         | 要写清什么，为什么这样规定                                   | 怎么检查                                     |
| :----------- | :----------------------------------------------------------- | :------------------------------------------- |
| 命名与类型   | 表名与字段名的单复数、时态统一；时间统一用 UTC 存储；状态用枚举并写清取值含义。命名不一致会让查询语义随作者变化 | 数据字典与实现比对；出现两种命名风格即判缺陷 |
| 主键与外键   | 主键类型统一；外键与级联行为写清；跨资源引用必须带归属字段。缺归属字段时，逐资源授权判定就无处落地 | 抽查涉及资源的表，是否都能一次取到归属       |
| 审计字段     | 创建时间、更新时间、创建人必填；变更留痕只增不改。没有审计字段就无法回答「这条记录谁改的」 | 抽查若干表是否齐备；缺少即补齐后再上线       |
| 迁移纪律     | 迁移文件只增不改；语句条件化可重跑；每次迁移写明回滚动作。上线后再改迁移文件会让环境之间不可比 | 迁移脚本审查；执行一次回滚验证可逆           |
| 数据字典     | 表与字段的含义只写一处，入库并随结构变更更新。含义分散时，同一个字段在不同模块有不同解释 | 变更说明与数据字典对照                       |
| 敏感数据分级 | 按公开 / 内部 / 敏感 / 个人信息分级，敏感字段清单与脱敏规则集中定义。分散定义的结果总是有遗漏 | 抽查日志与响应，含敏感原值即判失败           |
| 留存与删除   | 写明每类数据的保留期与到期清理方式；收到删除请求时列出全部副本（业务库、向量库、对象存储、缓存、备份） | 执行一次删除演练，逐项核对副本清单           |
| 跨存储一致性 | 同一份数据存在多处时，写明写入顺序与删除顺序，以及失败后的补偿动作 | 在删除中途制造失败，检查是否有残留与重试     |
| 测试数据     | 生产数据不进测试环境；需要样本时脱敏后导出。带真实数据调试本身就是一次泄露 | 抽查测试环境数据；含未脱敏的生产记录即判事故 |

## 评审与完成定义

| 条目                           | 要写清什么，为什么这样规定                                   | 怎么检查                                       |
| :----------------------------- | :----------------------------------------------------------- | :--------------------------------------------- |
| 完成定义（Definition of Done） | 一条变更完成的全部判定：场景全部满足、用例通过、门禁通过、文档同步、验证记录归档。没有完成定义时，「做完了」是主观判断 | 逐条打勾；勾不上的那一条就是未完成的部分       |
| 变更规模上限                   | 单次变更不超过一组任务或若干文件；超出即拆分。规模越大，评审越趋近于走过场 | 超过上限的变更应被拆回                         |
| 评审检查表                     | 人工评审看规约覆盖与业务判定（场景是否满足、授权判定是否正确、迁移是否可逆、提示词改动是否跑过评测）；Harness 审查看规范一致性；代码风格交由格式化工具 | 评审记录中应能看出三类分工各查了什么           |
| 责任人与时限                   | 谁批准、多久内响应、超时如何处置。没有责任人的评审请求会一直挂着 | 抽查是否存在超期未处理的评审请求               |
| 门禁必跑                       | 合并前必须执行门禁命令；不得跳过本地钩子，也不得放宽其中的检查项让结果变绿 | 抽查若干合并记录是否都能对应到一次门禁执行     |
| 例外书面化                     | 确有理由保留旧写法时，把例外写进规范本身并记录理由；不允许留在会话里的口头豁免 | 检索规范文件中的例外条目；会话里的豁免一律无效 |
| 证据归档                       | 变更说明、验证记录、评审结论归档到仓库的 docs/ 目录，按变更名可检索 | 按变更名检索，应能一次找到三份材料             |
| 复盘留痕                       | 失败与返工的原因记入变更说明或决策记录，作为下一次的输入     | 抽查一次失败是否有可检索的记录                 |
